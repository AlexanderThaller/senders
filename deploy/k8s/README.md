# Kubernetes

Kustomize manifests for the server. Nothing here builds the image — see the
repository README for that.

```
base/                  Deployment, Service, PodDisruptionBudget, config
overlays/production/   Redis + S3, 3 replicas, Ingress with TLS
overlays/single-node/  one pod, volume-backed, metadata in memory
```

```sh
kubectl apply -k deploy/k8s/overlays/production
kubectl apply -k deploy/k8s/overlays/single-node
```

Edit the host in `overlays/production/ingress.yaml` and the matching
`SENDERS_PUBLIC_URL` in its `kustomization.yaml` before applying either.

## TLS is required, not recommended

WebCrypto is only exposed in a secure context. Over plain HTTP the page loads
and then fails at the first key generation, so the service is unusable on
anything but `localhost` without TLS. The production overlay assumes
cert-manager and a `letsencrypt` ClusterIssuer.

## The two ingress settings that break uploads

Both are on the Ingress in the production overlay, and both are wrong by
default:

- `proxy-body-size` — the nginx default is 1 MiB, which rejects essentially
  every upload. Set it to `0` and let the server enforce `SENDERS_MAX_FILE_SIZE`
  itself; it returns a clean 413 where the ingress returns an opaque one.
- `proxy-request-buffering: "off"` — with buffering on, nginx writes the whole
  upload to its own disk before contacting the pod. That defeats the streaming
  path, delays the response by the length of the transfer, and can fill the
  controller's disk.

Read and send timeouts are raised for the same reason: a large transfer over a
slow link is one long-lived request, and the 60s defaults cut it off mid-file.

On a Gateway API setup these become the equivalent settings on the
`HTTPRoute`/`GatewayClass`; the constraint is the same.

## Prerequisites

The production overlay expects two things it does not create:

- **Redis-compatible metadata store** — Dragonfly, Valkey or Redis. Deploy it
  with its own operator or chart; a StatefulSet does not belong in this base.
- **S3-compatible object storage** — anything the AWS SDK can talk to. Set
  `AWS_ENDPOINT_URL` and `SENDERS_S3_PATH_STYLE=true` for MinIO, Garage or Ceph.

Both are required to run more than one replica. With `memory:` metadata or `fs:`
storage, a second pod knows nothing about the first pod's links and serves 404s
for roughly half of them. That is why the single-node overlay pins replicas to
one.

## The Secret

Not generated by kustomize, so that nothing sensitive lands in git. Create it
before the first apply — the production overlay marks it `optional: false`, so
the pod will not start without it.

```sh
kubectl -n senders create secret generic senders-secrets \
  --from-literal=SENDERS_SESSION_SECRET="$(openssl rand -hex 32)" \
  --from-literal=AWS_ACCESS_KEY_ID=... \
  --from-literal=AWS_SECRET_ACCESS_KEY=...
```

`SENDERS_SESSION_SECRET` must be the same for every replica and stable across
restarts. Without it the server generates a random key per pod, and sessions
break whenever a request lands on a different replica. It only matters when
`SENDERS_AUTH_MODE` is not `off`, but set it anyway — the failure is silent.

Add `SENDERS_OIDC_CLIENT_SECRET` here too when enabling login. Sealed-secrets or
external-secrets work unchanged; the Deployment only cares that a Secret of that
name exists.

### Or no Secret at all

A Kubernetes Secret puts the values in etcd, where anyone with `get secret` in
the namespace can read them. If you run a secrets manager that mounts files —
Vault with the secrets-store CSI driver, for instance — point the server at the
mount instead and create no Secret:

```yaml
env:
  - name: SENDERS_SESSION_SECRET_FILE
    value: /run/secrets-store/session_secret
  - name: SENDERS_OIDC_CLIENT_SECRET_FILE
    value: /run/secrets-store/client_secret
  # The AWS SDK's own file-based credential source; no S3 keys in the pod spec.
  - name: AWS_SHARED_CREDENTIALS_FILE
    value: /run/secrets-store/credentials
```

Nothing then needs to be synced into etcd. See the main README for what the
`_FILE` variables accept.

## Operational notes

- **Probes.** Readiness is `/healthz`, which checks Redis and object storage.
  Liveness is `/`, which is served from the image and touches nothing. They are
  deliberately different endpoints: if `/healthz` drove liveness, a Redis blip
  would restart every pod at once rather than just taking them out of rotation.
- **Start-up.** The server connects to Redis while starting and exits if it
  cannot, so a cold cluster shows `CrashLoopBackOff` until Redis is up.
- **Rollouts.** `terminationGracePeriodSeconds` is 120: in-flight downloads have
  that long to finish before the pod is killed. Raising it makes large transfers
  safer and every rollout slower.
- **The reaper** runs in every replica. Deletion is idempotent and the download
  budget is claimed with an atomic script, so this is safe — but the sweep
  interval is per replica.
- **Image tags.** The overlays use `latest`, which is fine for a first apply and
  wrong afterwards: nothing tells the Deployment the tag moved. Pin a digest or
  a release tag.
